What Claude Code Actually Does That ChatGPT Doesn't (A Non-Engineer's Take)

For about a year my workflow was: ask the chat assistant a question, get a block of code, paste it into a file, run it, watch it fail, paste the error back, get a revision, paste that in, run it again.

That loop is where I lived. And I got things done in it. But every single step of it was me acting as a courier between two systems that couldn't see each other.

Claude Code removes the courier. That's the honest one-line summary, and everything below is just me being specific about what that changes when you can't read the code you're carrying.

The difference isn't intelligence, it's access

Let me set the comparison up fairly, because "X beats Y" posts usually cheat here.

The model answering me in a chat window is very capable. Chat products have also added sandboxes and agent modes that run code somewhere. But none of them are looking at the folder on my laptop where my blog lives. They see what I paste. They produce text I have to place somewhere. The gap between their output and my working system is me, and I'm the unreliable part.

Claude Code runs in my terminal, in my project folder. It reads my actual files, edits them in place, runs commands, and reads what comes back out. Same underlying intelligence, completely different relationship to my work.

For an engineer that's a convenience. For a non-engineer it's the whole thing — because the courier steps are precisely the ones I'm bad at.

Example one: the garbled text

Early on, my site generator produced pages of nonsense characters instead of Japanese. Classic encoding problem, though I didn't know that word yet.

Here's how that goes with a chat window. I describe the symptom. I get asked which encoding I'm using, and I don't know. I get told to check, and I don't know how. I paste the script; I get a suggested fix; I paste the fix into the wrong place because I misjudge the indentation; it now fails differently. Round and round. On my own this class of problem eats an evening, and about 80% of that evening is me relaying information badly.

What actually happened: I said the output was garbled. It ran the script. It read the traceback itself, edited the file, ran it again, and looked at the resulting page. Fixed in a couple of minutes.

The change I care about isn't speed. It's that the diagnosis never depended on my ability to describe the problem accurately. It could go look.

Example two: the tables I broke without knowing

This one is my favorite, because it's a failure that a chat window could not have caught.

I'd been writing comparison tables in my articles using standard Markdown. My homemade generator didn't support tables — nobody had told it to — so it published them as mangled rows of pipes and dashes. On the live site. For weeks. I never noticed because I proofread in my editor, where the source looks fine.

When I did notice, the fix wasn't one file. It meant changing the renderer to understand table syntax, adding styling so the result didn't look terrible, checking whether the RSS output needed the same treatment, and rebuilding every previously published page.

I couldn't have described that job accurately, because I didn't know which files were involved. I said, roughly: "my tables are publishing broken, fix it." It went and found the pieces.

That's the second capability, and it's bigger than editing: it can work across a codebase I haven't read. A chat assistant can only help with the file I know to paste, which means my blind spots become its blind spots.

Two more, briefly: eight books and an unread log

I used Claude Code to generate eight English Kindle manuscripts in a single day. Full-length ones, roughly 30,000 words each.

I'm not holding that up as an achievement — I'll get to why in a second — but it's a clean illustration of the difference. A chat window can write you a chapter. Genuinely good ones. What it can't do is *be* the production line: create the folder structure, write chapter files to disk, keep eight separate projects straight, convert the finished text into ebook format, generate cover files, and hand you a directory you can actually work with at the end.

That's not a smarter model. That's a model with file access and a shell. Everything in that list is boring mechanical work, and boring mechanical work at volume is exactly what a chat interface cannot absorb, because every step needs a human to copy something from one window into another.

The important caveat: generating eight manuscripts turned out to be the easy part of publishing eight books, and two months later I have published exactly none of them. That's its own article. But the generation step itself was real, and it was only possible because the tool had hands.

The log I never opened

The automatic publishing pipeline behind this site died and stayed dead for over a month without my noticing. The cause was a trivial formatting difference in a scheduler file — wrong line endings for Windows.

The errors weren't hidden. They had been piling up in a log file the entire time, and I had never once opened it. When I finally asked what was wrong, the tool read the log, read the scheduler file, spotted the mismatch and fixed it.

I could not have pasted that log into a chat, because I didn't know it existed. Which is a fair summary of the whole difference: a chat assistant can only help with what you already know to show it.

What it doesn't do, and where I still get burned

I'd be selling you something if I stopped here.

It does what you asked, not what you needed. The broken tables were my fault, structurally. I never said "I'm going to use tables in my articles," so the generator never handled them. It executes the request precisely. Noticing what's missing from the request stays your job, and that's the job that actually requires taste.

Vague in, vague out. "Build me a nice blog" produced something forgettable. "Make it so that dropping a text file into this folder turns it into a published post" produced the thing I still use. The skill I've built over these months isn't programming. It's describing a finished state clearly enough that someone else could build it. That skill transfers to everything, incidentally.

Working is not the same as correct. Everything ran for months while quietly publishing broken tables. When I later went back and audited my own setup properly, I found several more things that were running and wrong. A running system provides no evidence that it's doing the right thing, and the tool won't volunteer that judgment.

You still have to check the output. Especially anything visual, and anything factual. It produces plausible work fast, and plausible-fast is the exact combination that makes people stop verifying.

Who I'd tell to skip it

If you want to hand a project over and not look at it again, this will hurt you. You'll get something that runs, you'll assume that means it's finished, and you'll find out in five weeks that it isn't. That's not a hypothetical, it's my experience twice over.

If you have something specific you want built, and enough stubbornness to keep asking "why is it doing that" — this collapses the distance between wanting a tool and having one, and it does it without you learning to program first.

I still use a chat window every day, for thinking out loud, for questions, for drafting. The two aren't rivals. One is for talking about the work. The other one does the work, in the actual folder, on the actual files. Once you've had the second thing, going back to being a courier is hard to stomach.
