Claude Code vs ChatGPT: What It Does That a Chat Window Can't

Written by Automating the Boring Parts

Claude Codetoolsnon-engineerbuild log

For about a year my workflow was: ask the chat assistant a question, get a block of code, paste it into a file, run it, watch it fail, paste the error back, get a revision, paste that in, run it again.

That loop is where I lived. And I got things done in it. But every single step of it was me acting as a courier between two systems that couldn't see each other.

Claude Code removes the courier. That's the one-line summary, and everything below is me being specific about what that changes when you can't read the code you're carrying.

Short answer: ChatGPT in a browser tab sees only what you paste into it. Claude Code works inside a folder on your computer, reads the files, runs them and reads the errors itself. Everything below comes from building and running this blog and the pipeline behind it, plus one browser extension.

The difference isn't intelligence, it's access

Let me set the comparison up fairly, because "X beats Y" posts usually cheat here.

The model answering me in a chat window is very capable. ChatGPT has also added its own ways to work on files, including a desktop app that can read and change files in a folder you pick, and OpenAI's Codex. Nothing on this site was built with those, so I'm not comparing them here. What I'm comparing is the way I actually worked before: a chat window that sees what I paste and produces text I have to place somewhere. The gap between its output and my working system was me, and I'm the unreliable part.

Claude Code runs in my project folder. It reads my actual files, edits them in place, runs commands, and reads what comes back out. It runs Anthropic's Claude models, not the ones behind ChatGPT, so this isn't a like-for-like model test. For me the bigger difference was where it works.

For an engineer that's a convenience. For a non-engineer it's the whole thing, because the courier steps are precisely the ones I'm bad at.

Example one: the garbled text

Early on, my site generator produced pages of nonsense characters instead of the text I'd written. Classic encoding problem, though I didn't know that word yet.

Here's how that goes with a chat window. I describe the symptom. I get asked which encoding I'm using, and I don't know. I get told to check, and I don't know how. I paste the script; I get a suggested fix; I paste the fix into the wrong place because I misjudge the indentation; it now fails differently. Round and round. On my own this class of problem eats an evening, and most of that evening is me relaying information badly.

What happened instead: I said the output was garbled. It ran the script. It read the traceback itself, edited the file, ran it again, and looked at the resulting page. Fixed in a couple of minutes.

What I care about is not the speed. The diagnosis never depended on my ability to describe the problem accurately. It could go look.

Example two: the tables I broke without knowing

This one is my favorite, because it's a failure that a chat window could not have caught.

Before this site existed, I'd been writing comparison tables in my articles using standard Markdown. My homemade generator didn't support tables, because nobody had told it to, so it published them as mangled rows of pipes and dashes. Live. For weeks. I never noticed because I proofread in my editor, where the source looks fine.

When I did notice, the fix wasn't one file. It meant changing the renderer to understand table syntax, adding styling so the result didn't look terrible, checking whether the RSS output needed the same treatment, and rebuilding every previously published page.

I couldn't have described that job accurately, because I didn't know which files were involved. I said, roughly: "my tables are publishing broken, fix it." It went and found the pieces.

That's the second capability, and it's bigger than editing: it can work across a codebase I haven't read. A chat assistant can only help with the file I know to paste, so my blind spots become its blind spots.

Two more, briefly: an extension and an unread log

On November 1, 2026, I had Claude Code build a Chrome extension that formats JSON. It took one day.

A chat window could have written me the code for it, file by file. What it can't do is test the result. Claude Code loaded the extension into Chrome on my laptop and ran 61 checks against it: formatting, error display, search, the paid features staying locked, and no network requests from the free ones. Then it measured how long a 50 MB file took to show up, with and without the extension.

None of that is clever. It's boring mechanical work, and boring mechanical work at volume is exactly what a chat interface cannot absorb, because every step needs a human to copy something from one window into another.

The caveat is the same one as everywhere else on this site: the extension still isn't in the store. Building it was the fast part.

The log I never opened

The same automatic publishing pipeline behind this site ran the first site I built on this pipeline, and there it died and stayed dead for over a month without my noticing. The cause was a trivial formatting difference in a scheduler file: wrong line endings for Windows.

The errors weren't hidden. They had been piling up in a log file the entire time, and I had never once opened it. When I finally asked what was wrong, the tool read the log, read the scheduler file, spotted the mismatch and fixed it.

I could not have pasted that log into a chat, because I didn't know it existed. Which is a fair summary of the whole difference: a chat assistant can only help with what you already know to show it.

What it doesn't do, and where I still get burned

I'd be selling you something if I stopped here.

It does what you asked, not what you needed. The broken tables were my fault, structurally. I never said "I'm going to use tables in my articles," so the generator never handled them. It executes the request precisely. Noticing what's missing from the request stays your job, and that's the job that actually requires taste.

Vague in, vague out. "Build me a nice blog" produced something forgettable. "Make it so that dropping a text file into this folder turns it into a published post" produced the thing I still use. The skill I've built over these months is describing a finished state clearly enough that someone else could build it.

Working is not the same as correct. Everything ran for weeks while quietly publishing broken tables. When I later had a fresh Claude instance check this site's own build-log post, it found the post quoting costs and visitor numbers that weren't this site's. That's in the 99-days post. A running system provides no evidence that it's doing the right thing, and the tool won't volunteer that judgment.

You still have to check the output. Especially anything visual, and anything factual. It produces plausible work fast, and plausible-fast is the exact combination that makes people stop verifying.

Who I'd tell to skip it

If you want to hand a project over and not look at it again, this will hurt you. You'll get something that runs, you'll assume that means it's finished, and you'll find out weeks later that it isn't. It has happened to me more than once.

If you have something specific you want built, and enough stubbornness to keep asking "why is it doing that", this collapses the distance between wanting a tool and having one, and it does it without you learning to program first.

I still use a chat window every day, for questions and for thinking out loud. But everything this site runs on, the generator, the publishing queue, the scheduled refill, was built by the tool that works in the folder. What it didn't remove is the part that decides whether any of it earns: reading what it made, listing it, and checking what is live. That's where my projects have stalled, with the digital products I never listed and 99 days without a post.
