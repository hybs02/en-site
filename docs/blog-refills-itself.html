My Blog Now Refills Itself Twice a Week. Run One Held a Post Back

Written by hybs02

build logautomationClaude Code

Twice a week now, at 10 a.m. on Wednesdays and Saturdays, Claude Code opens this site on its own, checks it, and adds a post to the queue if it's running low. No person approves anything first. The first run was on November 4. It wrote one post and refused to queue it. As I write this on November 5, it has run once. Since then, the November 7 run maintained a published post and queued a new one, and on November 11 the one post it wrote failed the gates and stayed in drafts.

Why I took myself out of the loop

In the post about the 99 quiet days, I described a refill job I'd turned into a Claude Code skill. It ended with me reading every draft and approving it before it went into the queue. I also wrote that the skill checks everything when I ask and nothing at all when I don't.

That second part was the real problem. A scheduled run that still stopped for my approval would only move the waiting from the queue to my drafts folder. Drafts would sit in a folder I don't open, the same way the queue had sat empty. So I told Claude Code to do the whole job on its own, approval included.

The same post said I couldn't get Claude Code to run unattended on my PC. Back in June I'd tried its cloud scheduler, which couldn't reach my setup, and a script that called it from the command line, which I never got working. What works now is simpler: the desktop app has scheduled tasks built in. A task is a prompt, a folder and a schedule. Mine runs on the cron line 0 10 * * 3,6. When the time comes, the app starts a fresh session, loads the blog skill, and follows a section written for runs nobody is watching. The order is fixed:

StepWhat happens
1Health check: days since the last post, posts in the queue, whether the live site responds
2Re-register the Windows Task Scheduler job that publishes on Mondays and Thursdays, if it has disappeared
3Read the title and opening of every published and queued post
4Re-read every queued post against the others and fix stale numbers
5Pick one published post and maintain it
6If fewer than four reviewed posts are queued, draft one
7Push the changes, deploy the fixes, and write a report

Step two matters here because, as the 99-days post said, this site never had a publishing job at all. It does now. The posts on November 2 and November 5 were the first on this site to go out at 7 a.m. with nobody at the keyboard.

Writing is step six. Everything before it is reading. A new post that contradicts an old one is worse than no new post, so the run has to know what the site already says before it adds anything.

Seven gates instead of me

Without my approval, the queue needs another lock. A draft has to pass seven checks. If it fails any one of them, it stays in the drafts folder and the report says why.

GateWhat has to be true
Machine checksZero errors on word count, links, hype phrases and stock AI phrases
Blind reviewA fresh Claude instance, with none of the drafting conversation, rates it "publish as is" or "publish after fixes"
Required fixesEvery point the reviewer marks as required is fixed, and factual ones are checked against the source files first
Second readIf there were three or more required fixes, the revised draft goes back to the reviewer and must come back with none
Commands runAny command or code in the post was run on my PC
Off-limits topicsNothing the site has decided not to write about
ConsistencyNo number or conclusion that disagrees with a published or queued post

There's one more rule about topics. The run can't ask me anything, so it may only pick topics it can write from my files, logs and saved notes. My reasons and feelings at the time aren't in any file, so a topic that needs them is off the table. If no topic fits, it writes nothing and reports "out of topics."

What the first run did

StepResult
Queue checkOne post was queued, the zero-products post, due November 5. It added one internal link
MaintenanceIt checked the eight-books post. That post and one other still said none of my books were on sale. Three were. It fixed both so the number matches everywhere
New postA 1,325-word draft. First review: three required fixes. Second review: one still open
Gate resultFailed the second-read gate. The draft stayed out of the queue
Queue after the runOne post, which went out on November 5. Then zero

The open point was a single sentence. The draft described an answer on a disclosure form as the obvious one, when it was a judgment call. The run rewrote the sentence to say so, but the rule says the second read has to come back clean, and there's no third round in the rules. So it stopped.

The easy failure for a system like this is to fill the queue no matter what. This one did the opposite, and the opposite is the state that cost this site 99 days: an empty queue and a publishing job that reports success. The difference this time is that the report said so.

The next day I went through the draft in a separate session, had that last point fixed, and approved it for the queue myself. That's the post about KDP listings, due out on November 9. That post and this one are the only two so far that went into the queue at my request instead of through the gates.

The maintenance step is the one I hadn't planned for when this site started. An old post stays frozen at the facts of the day it was written. On November 4 this site had four posts, and two of them still said none of my books were on sale when three were. That was half the site out of date. Fixing one old post per run means the older pages slowly catch up.

Where the report goes

Every run ends with a short report in the same shape. It lists new posts with each gate's result, fixes to queued posts, the published post it maintained, drafts it held back and why, and how many posts are left in the queue. On November 4, the held-back line is what told me this site would have nothing queued after November 5.

The report lives in the task's history in the desktop app. Nothing is sent to me when a run finishes. I have to open it.

The holes that are still open

There are two.

The first is that the task runs on my laptop. The app's documentation says tasks only run while the app is open and the computer is awake. If the laptop is asleep at 10 a.m., that run is skipped. When it next wakes or the app starts, the app runs one catch-up for the most recent missed time in the last seven days and drops anything older. So a Wednesday morning run can end up happening on Wednesday night, and two missed runs come back as one. There's a Keep computer awake switch under Settings > Desktop app, but closing the lid still puts the laptop to sleep.

The second is the one I traded for. No person reads a post before it goes out now. The gates are the only check, and whatever they miss will go live on a Monday or Thursday morning. A post sits in the queue for a few days before it goes out, so reading the report would let me pull it in time. That only works if I open the report.

In the 99-days post, I said the obvious fix for silence would be an alert that comes to me instead of a panel I have to open. I still haven't built one, and the report is another thing I have to go and open. The risk I'm guarding against now is a post going out that the gates missed, on a morning I didn't open the report.
