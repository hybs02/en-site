"Monitoring an Automated Blog: What My Dashboard Warns About"

Written by Automating the Boring Parts

This site had a one-screen dashboard watching it the whole time it went 99 days without a post.

The panel is a small desktop app that Claude Code wrote for me. It reads the same folders the publisher uses and shows when the next post goes out, how many finished posts are waiting, and whatever needs me. On the morning of November 11, 2026, it read:

TileShowsDetail
Next post11/12Thursday 7:00
Posts in the queue2Covers through Mon 11/16

In the panel's "Do now" list, the queue line was amber: two posts left.

I changed the rules behind that list on November 1. This post is about those rules: what earns a line there, and what I took out.

The September rules

The first version showed only the last publish date and the queue count. From late July it also put a red band across the top for a failed run, an empty queue, ten days without a post, or publishing switched off.

On September 26, Claude Code rebuilt the panel. The desktop screen and a phone screen had each been doing their own math, and that moved into one shared file. The warnings were split into red and amber and gathered into a "Do now" list the same day, with these rules:

LevelCondition
RedThe last scheduled publish failed
RedScheduled publishing is on and the queue is empty
AmberOne or two posts left in the queue
AmberScheduled publishing is off
AmberPublishing is on and ten or more days have passed since the last post

September 26 was day 63 of this site's 99 quiet days. The scheduled publisher had never been switched on and the queue was empty, so under those rules the line was amber: publishing off, nothing queued. The ten-day rule only applied while publishing was on, so it didn't fire.

So on the day the list was rebuilt, it already had a warning for this site. The queue stayed empty for another five weeks. I covered why in the post about the 99 days: the panel only talks while it's open.

A warning with nothing to do

On November 1, two posts went into this site's queue and the scheduled publisher was switched on for the first time. The next morning's run was set.

Under the September rules, the panel would have shown two amber warnings that day. One said two posts were left, which was fair: two posts is thin. The other said 99 days since the last post. That line was true, and it asked for nothing. It would have cleared itself at 7 a.m. the next day whether I read it or not.

The second line is the kind I wanted gone. This is alert fatigue at the scale of one person and one screen: a panel that shows amber every time I open it teaches me to stop reading amber, and the next amber line might be one that needs me.

Five warnings in, two left out

The rule the list has followed since November 1 fits in one sentence: it shows only things that stay broken unless I act.

LevelConditionWhat I do
RedThe last scheduled publish failedRead the log, fix the cause
RedPublishing is on and the queue is emptyRefill
RedPublishing is on and the publisher hasn't run for 8 days or moreCheck the PC was on at all that week, then the task's last result
AmberOne or two posts leftRefill
AmberScheduled publishing is off, or the job is missingTurn it on

A sixth, uncolored line isn't a warning. It says how many queued posts haven't been reviewed and so won't publish.

Two things no longer earn a line:

Left outWhy
A long gap since the last post, when the queue has posts and the next run is setThe next run fixes it without me
A site whose publisher has never run and isn't switched onIt hasn't stopped. It hasn't started. The panel marks it as dormant

The 8-day rule replaced the 10-day one, and they count different things. The old rule counted days since a post went out. The new one counts days since the publish script last wrote down that it ran, post or no post.

The job runs on Mondays and Thursdays, so the longest normal gap between runs is four days, and one missed run makes it seven. Eight days means two runs in a row didn't happen while the job is still registered. Either the PC stayed off or asleep the whole time (the task is registered to run as soon as possible after a missed start, so a single missed 7 a.m. run catches up the next time the PC wakes), or the task is failing before it starts. If the job has been deleted, the panel shows the amber "publishing is off" line instead. An empty queue already has its own red line. The old rule lumped those failures together, and they need different fixes.

The panel reads three things to decide all of this:

  • A small state file the publisher rewrites on every run: last run time, last result, last publish date.
  • The queue folder, where it counts the posts marked as reviewed.
  • Windows Task Scheduler, which it asks whether the job is enabled and when it runs next.

The queue and publishing-off lines carry a button for the next step. A queue warning copies a ready-made request for Claude Code to the clipboard: a refill, or a review if unreviewed posts are sitting in the queue. The "publishing is off" warning turns publishing on from the panel. The two red lines, a failed run and no run for 8 days, only open the blog's status view, and from there I still read the log myself.

The rule that would have missed this site

The second row of the left-out table has a cost, and this site is the example.

For its first 99 days, this site was exactly what the new rules call dormant. The publisher had never run, scheduled publishing wasn't on, and the queue was empty. Under the September rules that was an amber line. Under the rules I use now, it would be a "dormant" label, a one-line note that publishing hasn't started, and no line in "Do now."

I kept the rule anyway. A site I haven't started isn't a fault for a monitor to catch. It's a decision I haven't made, and a warning that sits there for 99 days is one I'd learn to skip, which is the same problem as the stale amber line. The cost is that the panel will stay quiet about a blog I set up and then never switch on.

A phone version

The panel also has a phone version. A small web server on my PC serves the same screen to the browser on my phone.

ChoiceDetail
One sourceDesktop and phone screens draw what a shared file computes, so they can't disagree
A key in the URLAny request without a random key is refused
Not on the internetReachable from my home network, or through Tailscale, a private network between my own devices
Opening filesOnly accepted when the request comes from the PC itself
Fresh numbersThe queue and schedule are read every time I open it

The key is there because the panel can publish. Another device on my home network that stumbles on the address gets nothing.

What the panel is for now

What ended this site's 99 days was a refill I asked for on November 1. What's meant to stop the next one is taking myself out of the step the panel kept pointing at. The panel told me to ask Claude Code for a refill, and I was the slow part of that chain. Since November 4 a scheduled Claude Code task does the refill on its own, which is the subject of the post about the blog refilling itself.

So the panel has a narrower job now. It checks whether the refill task is keeping the queue stocked. If "Do now" is empty, I close it. If there's a line, it's something the scheduled task couldn't fix or hasn't got to yet.

The amber "two posts left" line doesn't fully pass that test. The refill task drafts at most one post per run, twice a week, and the publisher takes two a week. Going in and coming out are the same speed at best, so the queue can't climb back above two, and the amber line is on almost all the time. Every refill that fails its gates leaves the queue one post shorter. On November 11 the refill run drafted this post, the draft failed the gates and stayed in drafts, and the November 14 run fixed it and queued it. After this post went out on November 16, the queue was empty. I haven't changed the amber rule, or how many posts a run may draft.

The panel also still says nothing unless I open it, and the phone version goes dark when the PC does. An alert that reaches my phone when the queue hits zero isn't built yet.

If I were asking Claude Code for a panel like this again, I'd say:

Build a one-screen panel for my scheduled blog. Have the publish script rewrite a small state file on every run, including runs with nothing to publish: last run time, last result, last publish date. The panel reads that file, counts the reviewed posts in scheduled/, and asks Windows Task Scheduler whether the job is enabled and when it runs next. List a warning only if it stays broken unless I act: a failed run, an empty queue while publishing is on, no run for 8 days or more while publishing is on, one or two posts left, or publishing switched off. Don't list a long gap since the last post when the queue has posts and the next run is set. If the publisher has never run and isn't switched on, label the site as dormant instead of warning. Give each warning a button for the next step.
