A $0 Self-Updating Blog on GitHub Pages: The Whole Setup

Written by Automating the Boring Parts

The site you're reading costs me nothing to run. It lives on GitHub Pages at a github.io address, the certificate comes with it, the analytics run on a free service, and the software that turns my drafts into web pages is a Python script on my own laptop.

I'm not an engineer, and I didn't write this generator in any sense that would impress one. I described what I wanted, Claude Code wrote most of the code, and I spent the rest of my time finding out which parts didn't work.

What it is, and why it isn't WordPress

There's no admin panel, no database and no login. The setup has four moving parts:

  • Articles live as plain text files (Markdown) in a folder.
  • A Python script reads that folder and generates HTML: article pages, the index, tag pages, an RSS feed, a sitemap.
  • The generated files get pushed to GitHub, and GitHub Pages serves them.
  • A scheduled task on my PC takes the next finished article from a queue folder at 7 a.m. on Mondays and Thursdays and runs that whole chain.

That task only publishes. Writing is a separate job: twice a week a Claude Code scheduled task checks the queue, and when it's low, drafts a post and decides on its own whether to queue it. That half is in the post about the blog refilling itself. The queue spreads the posts out, one at a time.

The generator uses nothing but Python's standard library. There are no packages to install, so there's nothing that breaks because someone else's project moved on.

I also built in a gate. A queued article only publishes if its header says reviewed: true, and that line only goes in after the draft passes the machine checks and a blind review by a separate Claude instance. Automating publication without a quality check just means thin posts go out on a reliable schedule. The gate only covers the queue: a file dropped straight into the articles folder goes live on the next build.

Why not WordPress

Self-hosted WordPress needs a server, and a server is a monthly bill during a stretch where the site earns nothing. WordPress.com has a free plan, but it puts its own ads on your site and doesn't let you install plugins. I knew the zero-revenue stretch was going to be long, and a recurring charge against zero pushes you toward filler posts and early ads.

The other reasons were upkeep and automation. Plugins need updating, and I wanted something I could leave alone for a month. And if an article is a text file in a folder, "publish one post" is a file copy and a few commands, while publishing inside a CMS means scripting a web interface that changes whenever the vendor redesigns it.

The downside: this setup is bad if you want to write from your phone, and bad if you care about design. You get a fast, plain site and full control.

GitHub Pages is free for public repositories. Published sites are limited to 1 GB, with a soft bandwidth limit of 100 GB a month, which a small text blog won't come near. One condition worth reading before you monetize: GitHub says Pages is not intended for, or allowed to be used as, free hosting for an online business or an e-commerce site. I haven't put ads on this site, so I haven't had to find out where that line is.

If you want your own domain, that's the one recurring cost: the registration fee, paid every year. You'd also have to set up DNS, and that's a step this site skips.

The AI subscription I used to build this is not free. I'd pay for it anyway for other work, so I don't count it against the blog, but that's an accounting choice and you should know I made it. The other cost is time. The pipeline took about half a day to get working, and this site reuses those scripts. New posts are drafted by the scheduled Claude Code run, not by me.

Setting it up

These are the steps, in the order I'd do them again.

  1. Make two repositories. The source (drafts, scripts, settings) goes in a private one. Only the generated HTML goes in a public one, because free GitHub Pages needs a public repository. That way the drafts and the automation stay private.
  2. In the public repository, open Settings → Pages, choose "Deploy from a branch", and pick the main branch and the /docs folder. My deploy script copies the generated site into a docs folder, so the setting has to match where your files land.
  3. Put the site's full address in the generator's config. The RSS feed, the sitemap and the social preview image all use absolute links, and they come out wrong without it.
  4. Write a small .cmd file that runs the publish script with the full path to Python, and register it in Windows Task Scheduler on the days you want posts to go out. The task only runs if the PC is on at that time, so in the task's Settings tab, tick "Run task as soon as possible after a scheduled start is missed".
  5. Mark a draft reviewed: true and put it in the scheduled folder. Run the publish script with --dry-run first, which only reports which file would go next. Then run it for real once by hand and watch the whole chain work.

What to ask for if you build your own

My scripts live in a private repository, but the spec fits in a few lines, and that's what Claude Code needs. This is the request I'd make today:

Build a static site generator in Python using only the standard library. It reads Markdown files with a header (title, date, slug, description, tags) from articles/ and writes article pages, an index, tag pages, an RSS feed and a sitemap into docs/. Use the base_url from config.json for every absolute link.

Then build a publish script. It picks the lowest-numbered file in scheduled/ whose header says reviewed: true, sets its date to today, moves it to articles/, runs the generator, and pushes. Give it a --dry-run mode that only reports which file would go next, and make it write every run to a log file.

Then a deploy script that copies docs/ into a clone of my public repository and pushes it, and a .cmd file that runs the publish script with the full path to Python.

Where a non-engineer gets stuck

Garbled text. My first generated pages came out as walls of garbage characters. The script worked fine. Windows and Python simply disagreed about which text encoding to use. Claude Code found it in a couple of minutes by running the script and reading the error, and the fix was one line specifying UTF-8.

Two Pythons. Windows can end up with more than one Python. Typing python reached one copy while the real installation was somewhere else. That's harmless when you run things by hand and breaks the moment a scheduled task starts them in a different environment. The fix is to find the real one and write its full path into the .cmd file. where.exe python lists every copy Windows can see, in the order it tries them. In PowerShell, plain where means something else and prints nothing, so type the .exe. A path that ends in WindowsApps is a shortcut to the Microsoft Store, not a real install. Then ask the copy you actually use for its own path:


where.exe python
python -c "import sys; print(sys.executable)"

Analytics that undercount. I can't route a github.io address through Cloudflare, because I don't control its DNS, so the only way to count visitors is a small tracking script on each page. Ad blockers often stop that script, and anyone whose browser blocks it doesn't get counted.

The month it stopped and I didn't notice

This happened on the first site I built on this pipeline, before this one existed.

I built the automatic publishing, watched a post go out on schedule, and felt done. Some weeks later I looked again. It had been dead for over a month.

The cause was the scheduler's .cmd file. It had been saved with Unix-style line endings, the invisible characters at the end of each line, and Windows expects its own. The errors had been piling up in a log the whole time, and I never opened it.

What I took from that: a scheduled job that fails doesn't tell you. I now save .cmd files with Windows line endings on purpose, and I look at the publish log once a month.

Where this site stands

The first posts went up by hand on July 25, 2026. Every post since then has gone out through the queue, at 7 a.m. on a Monday or a Thursday, with nobody at the keyboard. The long gap after those first posts is in the 99-days post.

I'm not quoting a visitor number. I haven't looked at this site's analytics closely enough to trust a figure, and as above, the tracking script undercounts the readers most likely to be here. Revenue is zero.

The infrastructure part works. It costs $0 a month and a non-engineer can run it. Whether anyone reads the posts is a separate question.

The low cost is what lets me keep going. At $0 I can be wrong for a long time. At $30 a month I think I'd have added affiliate links by week three.
